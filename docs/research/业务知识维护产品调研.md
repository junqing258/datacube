# 从数据目录到业务知识维护：产品调研与 DataCube 建议

调研日期：2026-11-25。范围：官方文档的能力与流程对比，不是实际部署评测；不以此判断各产品在所有版本和付费版本中的完整能力。下文“局限”指机制对 DataCube 场景的适配判断，不代表产品不存在其他能力。

## 1. 结论

当前原型的数据目录以数据集卡片和指标列表为主，缺少编辑入口、变更流程、知识来源、作用范围、验证实例与失效处理。问题不止是名称难懂，而是尚未设计知识从产生到发布再到更新的生命周期。

建议将数据目录与业务配置合并为“业务知识”，按销售、库存、履约等业务主题组织。首页使用业务概览，维护页采用结构化编辑与说明文档结合，并引入查询实例、版本与影响提示。页面仍不增加 AI 会话入口，外部 Agent 通过 MCP / Skill 检索正式版本和提交修改草稿。

此结论是基于以下机制比较做出的产品建议，尚未做用户可用性验证，也未据此修改当前原型。

## 2. 产品比较

| 产品 | 已核实的机制 | 对可维护性的启发 | 对容易理解的启发 | 对本项目的适配判断 |
| --- | --- | --- | --- | --- |
| Metabase | 表字段描述、术语表、关联、可复用计算、精选来源；系统提示用于约定而非事实 | 知识附着于对应对象，降低重复定义 | 通过业务名称和术语衔接用户说法 | 适合底层元数据；DataCube 还需跨对象的主题视图与编辑流程 |
| Wren AI OSS | 结构语义、业务规则、确认的问句与 SQL 分开保存，可提交到仓库，索引可重建 | 规则与案例有持久记录，避免只存在对话中 | 业务规则和具体问题比单独字段说明更直观 | 与外部 Agent / Skill 的方向接近；不宜要求业务人员直接编辑文件 |
| Snowflake Cortex Analyst | 按业务域组织语义视图，指标与筛选定义，已验证问句及 SQL，支持评估和迭代建议 | 用查询实例验证知识变更，而非仅检查说明是否齐全 | 业务域、同义词和常见问题提供理解路径 | 借鉴机制，不能将 Snowflake 实现直接套到 MySQL 和自定义 API |
| Lightdash | 独立 YAML 模型，仓库连接或 CLI 部署，部分变更可回写 PR | 结构化定义可审查，减少页面和代码各维护一份 | 指标、维度是业务表述，但 YAML 仍主要面向开发者 | 适合开发者辅助维护；需另提供业务摘要与表单 |

### 2.1 Metabase：对象说明与精选业务来源

官方文档将 AI 上下文分为描述、术语、关联、计算定义和精选内容，并建议系统提示保存行为约定，而将业务事实放到对应元数据或定义中。[Metabase：配置 Metabot 上下文](https://www.metabase.com/docs/latest/ai/configure-metabot-context)

产品启发：不能用一个巨大提示词代替业务知识。字段说明、计算和业务词汇应绑定稳定对象；DataCube 的主题页面可以聚合展示这些对象，而不复制定义。

### 2.2 Wren AI：结构、规则、实例分别维护

当前 OSS 文档将 MDL 结构语义、业务规则、确认的自然语言与 SQL 实例，以及派生检索索引分开；前几类作为可检查文件保存，索引可重建。[上下文学习机制](https://docs.getwren.ai/oss/concepts/agent_learning)

项目结构进一步区分模型、关联、规则、术语、指标说明、注意事项与 SQL 案例。[MDL 结构参考](https://docs.getwren.ai/oss/reference/mdl)

官方 refinement 流程支持从文档、SQL 历史与业务补充中完善上下文。不同页面对于自动应用与等待审阅的描述存在差异，因此本报告不将“所有自动改动都必须人工批准”作为已证实的统一行为。[完善答案质量](https://docs.getwren.ai/oss/guides/refine)

产品启发：DataCube 可提供按主题维护的“规则”和“常见问题”，并让外部 Agent 生成草稿。是否发布由平台权限与校验决定，不依赖外部 Agent 自我声明正确。

### 2.3 Snowflake：业务域与可验证实例

官方建议按销售、营销等业务域组织语义视图，从业务使用者角度描述数据，并结合描述、同义词、关系、指标和筛选持续迭代。[语义视图建模最佳实践](https://docs.snowflake.com/en/user-guide/views-semantic/best-practices-modeling)

Verified Query Repository 存放问题与对应 SQL，可附验证人、时间，并供相似问题参考。这是提高准确性的参考机制，不保证新问题或新数据上的结果必然正确。[已验证查询库](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)

官方还提供从 Agent 日志经问题分类、业务专家复核，再完善语义与验证案例的示例流程；这是 cookbook 实现参考，不能视为所有部署默认开启的功能。[反馈完善示例](https://docs.snowflake.com/en/developer-guide/cortex-ai-cookbook/refinement-loop-from-agent-logs)

产品启发：每个关键指标不仅要有公式，还要有代表问题、预期计算方法和可执行验证。通过真实使用反馈更新知识。

### 2.4 Lightdash：定义与维护工具衔接

Lightdash 的独立 YAML 模型描述现有仓库表，支持通过仓库连接编译刷新或 CLI 部署；GitHub 接入支持将自定义字段及 AI 建议的变更作为 PR 回写。[Lightdash YAML](https://docs.lightdash.com/semantic-layer/yaml)

产品启发：可提供表单与可导出的文件表示，但必须选定唯一正式来源。首版不建议实现 UI 和 Git 无约束双向写入。

## 3. 对当前原型的诊断

1. 以技术数据集为中心，业务人员不知道为解决什么问题进入。
2. 数据目录与业务配置拆开，指标说明和定义容易重复。
3. 当前模型弹窗只是表单示意，未根据不同指标展示真实公式、来源与适用条件。
4. 没有区分说明文字、可执行规则与历史案例，Agent 难以判断哪些内容具有约束力。
5. 缺少负责人、状态、修改原因、变更版本、影响范围与验证结果。
6. API 仅显示“参数化 API”标签，未说明允许的参数、返回粒度、可拆分维度和不可执行操作。

## 4. 建议的信息结构

保留“数据接入”负责连接与技术结构，将“数据目录”和“业务配置”合并为“业务知识”。

业务知识 → 销售经营 / 库存管理 / 订单履约 → 概览、指标口径、业务规则、常见问题、数据映射、变更记录。

技术对象属于数据连接，知识主题引用它们。一个数据集可被多个主题引用，同一指标只保留一个正式定义，主题仅做引用；空间仍负责内容组织和访问范围，不能由主题取代权限体系。

### 概览

用日常语言说明：能回答什么、不能回答什么、数据覆盖范围、更新时间、负责人。提供“本月净销售额”“渠道变化”“库存周转”等问题示例，不设置聊天框。

### 指标口径

业务人员先看到业务含义、包含与排除项、时间规则、单位、示例、适用维度及限制。开发者展开查看计算表达式、表字段、API 操作和依赖。

### 业务规则

每条规则包含说明、适用对象、来源与负责人。能结构化执行的过滤、聚合约束存为结构化规则；只能解释的注意事项保留文档形式，不暗示其已被执行层强制保证。

### 常见问题与验证实例

每条实例包含问法、参数、依赖指标版本、基准 SQL 或 API 请求、预期结果或关系断言、验证人及验证时间。动态数据优先比较同一快照中的基准与生成结果，或使用稳定测试样本，不能长期硬编码“销售额必须等于某个数”。

### 数据映射

展示业务概念对应哪些表、字段或 API 参数，供开发者维护。API 额外维护分页、缓存、返回粒度、聚合限制和错误含义。

## 5. 维护工作流

资料或外部 Agent 提案 → 草稿 → 结构与引用校验 → 查询实例验证 → 查看差异及受影响看板 → 发布 → 记录版本。

- 初始建设：开发者选择数据范围并导入技术元数据，只补充关键业务主题，不要求先填完所有字段。
- 日常维护：业务人员修改说明或提议口径，开发者维护计算与映射，按角色授权发布。
- 变更影响：字段删除、类型变动和指标口径调整标记依赖对象为“待复核”；阻止失效定义继续执行或明确返回错误。
- 反馈闭环：外部客户端可通过 MCP 提交问题反馈或修正建议，但平台不能默认拥有外部聊天记录。
- 版本：说明性修改与改变计算结果的修改区分展示。旧版图表固定引用版本，迁移前显示影响范围。

这些都是 DataCube 建议能力，不能当作已经实现的功能。

## 6. 指标示例：净销售额

业务含义：统计选定时间范围内支付订单的支付金额扣除退款金额。

必须进一步确认：退款按支付订单归属期扣除，还是按退款发生期扣除；是否排除测试订单；币种如何处理。未确认时显示待确认事项，不自动生成正式公式。

业务界面显示“是什么、怎么算、按什么时间、包含什么、不能怎么用”；技术页显示实际表达式和映射。业务规则例如“排除测试订单”需绑定执行过滤，不能只写进一段说明。

## 7. MCP / Skill 的建议边界

- 按业务主题、指标、同义词和问题实例检索知识，按需取详情，不整包注入。
- 返回对象 ID、正式版本、状态、来源及适用范围，沿用数据权限。
- 查询绑定实际采用的指标版本。
- 支持提交知识草稿、查看校验结果与变更影响；发布使用独立权限。
- Skill 保存使用流程和通用操作约定；企业具体口径放在平台统一维护，避免多个 Skill 副本漂移。

## 8. 优先级与待讨论

首版优先：业务主题、指标业务摘要与技术映射、规则作用范围、问题实例、草稿与发布、变更历史、按需 MCP 读取。

后置：完整血缘平台、复杂审批、Git 双向同步、自动抽取大量文档、知识图谱可视化。

下一轮原型建议先验证“销售经营主题 → 净销售额 → 修改退款口径 → 查看影响与验证 → 发布”这一条维护路径，同时验证普通业务人员是否能仅凭概览理解可用能力。
