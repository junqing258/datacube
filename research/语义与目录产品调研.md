# 语义与目录产品：知识维护机制调研

调研日期：2026-11-25。限定为官方文档与官方产品说明；不是采购或部署验证。目标场景：DataCube 面向业务人员，开发者辅助，内网部署，数据来自 MySQL、Postgres 和 API，页面没有 AI 对话，AI 通过 MCP / Skill 接入。

## 结论与边界

**建议：把维护对象从“数据目录条目”升级为“业务口径”，同时保留可执行定义与维护流程。** 业务人员需要看到“怎么算、什么情况下不能用、谁负责、哪些报表受影响”，开发者需要看到字段映射、关联与校验。目录负责找到对象，语义层负责执行口径，协作机制负责让口径持续可信。这是本调研的设计推论，不是任一产品的完整现成功能描述。

以下区分事实与建议。Cube 的托管工作区能力不等于 Cube Core 内网开源部署自带；dbt Semantic Layer 的平台前提也不等于可直接嵌入本项目。研究重点是机制借鉴。

## 1. dbt Semantic Layer / MetricFlow：把口径定义成可检查的结构

**已核实事实**

- MetricFlow 根据 YAML 配置构建语义图；语义模型连接 dbt 模型，通过实体描述关系。最新规范将语义模型嵌入模型配置，而不是继续照搬旧的顶层独立写法。[Semantic models](https://docs.getdbt.com/docs/build/semantic-models)
- 官方规范明确区分语义模型、指标、维度，以及模型内和跨模型指标的定义位置；同一文档仍保留新版、旧版选择，说明配置版本必须显式管理。[Semantic Layer configurations](https://docs.getdbt.com/reference/semantic-layer-reference?version=2)
- 官方提供开发阶段查询、验证指标，以及在 CI 验证语义节点的工作方式。[官方 FAQ 源文件](https://github.com/dbt-labs/docs.getdbt.com/blob/current/website/docs/docs/use-dbt-semantic-layer/sl-faqs.md)
- 平台 Semantic Layer 设置要求 dbt 平台账户、环境及受支持的数据平台；列举的平台含 Postgres，未列 MySQL 或任意 HTTP API。[Administer the Semantic Layer](https://docs.getdbt.com/docs/use-dbt-semantic-layer/setup-sl)

**对 DataCube 的建议**

- 将“订单金额”拆成机器可检查的聚合、过滤、时间字段、允许维度、关系，而非只保存说明段落。自然语言解释必须链接到同一份可执行口径。
- 配置以规范版本标识；开发者可以导出到 Git、提交评审与回归，但业务维护不要求直接编辑 YAML。
- 借鉴语义校验机制，不直接假定 dbt 适用于所有数据源。API 数据需要先约定返回粒度、稳定主键、分页、时区、更新时间和快照一致性；这些是 DataCube 的适配设计要求。

## 2. Cube：内部模型与业务消费视图分开

**已核实事实**

- Cube 模型中的 cube 包含维度、度量和关联等结构；`title` 提供显示名称，`description` 提供可读解释，并可通过 API / 集成暴露。`meta` 支持附加元数据，文档也说明 `ai_context` 的用途。[Cubes reference](https://docs.cube.dev/reference/data-modeling/cube)
- 官方产品说明将 views 描述为对数据图的选定切片，用于控制向消费端暴露的指标、维度与关联方向；同时介绍代码和可视化建模、Playground、开发环境验证与版本控制工作方式。此处为产品能力声明，未实测其不同套餐与部署版本。[Data Modeling](https://cube.dev/product/data-modeling)
- 托管 Cube Cloud 官方说明支持 GitHub 自动部署，并在 Development Mode 提供个人 API 地址进行试验，再提交和推送变更；这不能推导为内网 Core 自带相同协作界面。[Cube Cloud announcement](https://cube.dev/blog/announcing-cube-cloud)
- 2026 年 View Groups 将视图按业务领域或用途分组，配置显示标题、说明，并呈现在消费端选择器和 REST 元数据响应中。[View Groups changelog](https://cube.dev/changelog/2026-05-08-changelog-view-groups)

**对 DataCube 的建议**

- 业务首页优先显示“销售分析”“履约分析”等主题及其可用口径，底层表、字段和 join 放在技术映射层。一个主题只暴露适合一起使用的指标与维度。
- 让页面、查询服务、MCP 读取同一个已发布语义版本；AI 补充上下文是该对象的属性，不另建一套易失真的 AI 文档。
- 采用“草稿预览 → 校验 → 差异确认 → 发布”的最小流程。Git 是开发者的集成接口，业务页面显示中文差异，例如“退款现在从净销售额扣除”。

## 3. OpenMetadata：知识维护不仅是填写说明

**已核实事实**

- 术语支持名称、显示名称、必填解释、同义词、相关术语、引用、负责人和多个审核人，也支持父子层级及 CSV 批量导入。[Create Glossary Terms](https://docs.open-metadata.org/v1.12.x/how-to-guides/data-governance/glossary/create-terms)
- 数据资产元数据有历史版本：描述、标签、负责人变动增加次版本；删除列等不兼容变更增加主版本；页面可追踪变更历史。这是实体版本机制，不能等同于 Git 分支与合并。[Data Asset Versioning](https://docs.open-metadata.org/v1.12.x/how-to-guides/guide-for-data-users/versions)
- 用户可以围绕资产提出描述或标签的创建、更新任务，默认指向资产负责人；没有负责人时可分配用户或团队。所引用页面为 SNAPSHOT 文档，应在选定稳定版本后复核。[Create Tasks](https://docs.open-metadata.org/v1.13.x-SNAPSHOT/how-to-guides/data-collaboration/tasks)
- 1.9 官方发行说明介绍术语审批流程历史界面，展示工作流进度、失败与任务创建。[Glossary Workflow History](https://docs.open-metadata.org/v1.12.x/releases/1.9-release)
- Data Contract 可约束资产应具备的描述、负责人、领域，并引用数据质量测试作为合规条件；文档把这些要求与数据测试分开描述。[Data Contracts specification](https://docs.open-metadata.org/v1.12.x/how-to-guides/data-contracts/spec)

**对 DataCube 的建议**

- 以术语及同义词解决“客户 / 买家 / 采购方”能否互换的问题，但术语解释不能替代计算规则。
- 对每条口径提供“报告问题”，提交时自动带入口径版本、当前筛选条件和相关报表；负责人收到待办并可以修订、解释或拒绝，处理结果可追踪。
- 区分文档完备校验、结构合法校验和数值正确校验。口径填写齐全不代表计算正确；数据测试通过也不代表符合业务含义。

## 4. 建议的最小维护对象与闭环

本节全部是设计建议，需结合 DataCube 现有结构取舍。

| 对象 | 业务人员维护与理解 | 开发者辅助 | 发布前检查 |
| --- | --- | --- | --- |
| 业务术语 | 名称、别名、解释、正反例、负责人 | 绑定指标 / 字段 | 同义歧义、重复定义、无人维护 |
| 指标口径 | 业务含义、单位、适用场景、包含 / 排除项、时间口径 | 聚合表达式、过滤、默认时间字段、粒度、允许维度 | 可解析、可执行、参考样本结果、与旧版差异 |
| 业务主题 | 本主题能回答什么、包含指标 / 维度 | 数据映射、关系、权限 | 非法组合、重复累计、下游影响 |
| 反馈任务 | 问题、样例、期望、处理意见 | 定位与修复 | 修复是否覆盖原问题、是否要变更版本 |

建议先实现一个贯穿路径：业务人员打开“净销售额” → 看见含税/退款/支付时间口径与计算示例 → 发现不一致并反馈 → 负责人修改草稿 → 开发者协助映射与样本验证 → 显示口径差异及受影响报表 → 发布新版本。将这个闭环做完整，比先扩大资产类型更能验证知识是否可维护。

MCP / Skill 建议首先提供按业务主题检索、读取已发布定义、获取允许查询组合、预览查询和提交修订建议的能力。每次返回稳定对象 ID 与版本；涉及执行的权限继续由查询服务实施。这里的工具边界是 DataCube 建议，不是对上述产品既有 MCP 能力的断言。
